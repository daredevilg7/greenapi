# MAX Chat — дизайн и требования

## Цель
Тестовое задание React: отправлять и получать текстовые сообщения MAX через GREEN-API. До подключения пользователь выбирает телефон или компьютер. Результат готовится локально; репозиторий и сервер пользователь предоставит позже. Сценарий согласован сообщением «делай» от 2026-10-04.

## Интерфейс
- Первый экран: компактный выбор двух устройств, фирменный знак MAX, спокойная типографика и интерактивные превью.
- Телефон: тёмный MAX внутри фронтального макета iPhone 17 с Dynamic Island, системной строкой и нижним индикатором. Мобильный референс определяет оформление чата: тёмный космический узор, серо-фиолетовые входящие, фиолетовый градиент исходящих.
- Компьютер: светлый MAX по референсу: узкая панель навигации, список чатов, белая шапка, голубой космический фон и поле сообщения внизу. Без внешнего макета компьютера.
- Основная функциональность: новый чат по номеру, выбор чата, текстовое сообщение, получение ответа, состояния отправки, поиск по локальным чатам. Звонки и вложения отсутствуют: задание ограничено текстом.
- Подключение: idInstance и apiTokenInstance, дополнительное поле apiUrl. Ссылки на кабинет и инструкцию настройки. Токен хранится только в оперативной памяти до выхода/перезагрузки.
- Демонстрационный режим явно обозначен, использует локальные диалоги и ответы; не вызывает API. Он позволяет осмотреть обе версии без ключей.
- Смена устройства сохраняет сессию и диалоги. Выход очищает реальные сообщения и ключи.
- На узких экранах десктопный режим становится двухэкранным: список → переписка. Макет телефона масштабируется без обрезания.
- Русские подписи, семантические кнопки, клавиатурная навигация, доступные диалоги, уменьшение анимаций при prefers-reduced-motion.

## Архитектура
React + TypeScript + Vite. Отдельные модули транспорта GREEN-API, модели переписки и представления. Без серверной части и внешнего хранения; стандартная статическая сборка dist. Использовать стандартные шрифты MAX для верности референсу; оригинальные публичные ресурсы MAX по возможности включить локально и указать источник.

## API и ошибки
- Проверять авторизацию через getStateInstance и настройки уведомлений через getSettings.
- Проверять телефон РФ/РБ и получать chatId методом checkAccount. Отправлять через sendMessage; максимум 4000 символов.
- Получать уведомления последовательным long polling receiveNotification с receiveTimeout=30. Применять событие к модели до deleteNotification; удалять также неподдерживаемые события, чтобы очередь продолжала работать.
- Повторно пришедшее событие не дублирует сообщение. Для удаления неуспешно подтверждённого события использовать повтор той же квитанции.
- Обрабатывать текстовые и расширенные текстовые уведомления, исходящие события и статусы sent/delivered/read/failed. Статус sent не означает доставку.
- Ошибки сети повторяют получение с ограниченной задержкой, ошибки авторизации прекращают цикл. Смена сессии/выход прерывает запросы; поздний ответ не изменяет новую сессию.
- Не повторять неуспешную отправку автоматически: после неоднозначного сетевого результата повтор может создать дубликат. Показывать ручной повтор с ясным сообщением.
- Обрезать сообщения об ошибках до понятных пользовательских формулировок без URL/токена.

## Проверка
Автоматические проверки критичной логики: нормализация номера, ограничения сообщения, сопоставление chatId, дедупликация, обновление статусов без понижения, порядок обработки/подтверждения очереди, отмена и восстановление после ошибки. Сборка TypeScript + Vite. В браузере проверить выбор устройства, подключение/демо, создание чата, сообщения, смену устройства, клавиатуру и узкие размеры.

## Граница проверки
Проверка реальной отправки и ответа требует авторизованного MAX-инстанса и получателя. Без ключей проверяются протокол, обработка событий и демонстрационный сценарий; реальная доставка не заявляется подтверждённой.
